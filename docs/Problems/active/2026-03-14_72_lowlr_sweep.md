  - final `all_ex_root=0.101969` vs current `72` `0.112074`
  - final `leg=0.186385` vs current `72` `0.296389`

  - vs candidate `71`, final `all_ex_root: -0.005095`
  - vs candidate `71`, final `leg: -0.028660`
- updated recommendation: **try `72 lr=1e-4` first** before changing `72` loss semantics

## Updated answer

### Does lower-LR `72` fix the problem?

- yes
- the attribution diagnosis was correct: unchanged `72` was mainly over-stepping the cleaner candidate `71` handoff
- lower LR directly fixes that without changing `72` objective semantics

### Which lower LR is best?

- best tested: **`72 lr=1e-4`**

### What should be tried next?

1. promote a confirmatory downstream continuation from `candidate 71 (lr=3e-4) -> 72 (lr=1e-4)`
2. if a cheaper backup is needed, `72 lr=5e-4` is already good enough to beat current `72`
3. only if `lr=1e-4` later shows downstream issues should we revisit gentler `72` semantics

## One-sentence answer

- `72` 的问题本来就是 early overshoot；把 `72 lr` 从 `1e-3` 降下来以后，这个前 20 步的 leg-side 过冲被直接压住了，而 `lr=1e-4` 甚至不只是“少吐回去”，而是把 `candidate 71` 的 aggregate 优势继续放大成了新的 `72` 最优结果。
